Magpie reference

Every function of the package, its parts and its two doors, with the design notes that decided them. The tour is the Magpie book; the functions here are called qualified (magpie.latest[…], kafka.serve[…]).

The log: use magpie

Import with use magpie; every function is called qualified (magpie.put[…]). The log as a directory of batch files, written in Crow on the sys layer (design rule 20): each commit is one file, written once (magpie.merger's write_batch, the sequencer's flush) — a frame given a position per row in a column _pos, its rows sorted by the key columns, in row groups of a few megabytes, and in the file's index the statistics a reader prunes by per column per group (min, max, the missing and distinct counts and a bloom filter, a filter over the words of each text column indexed), read on demand: a reader of two columns of a thousand reads two columns' index and two columns' chunks. The file is Magpie's own format (magpie.fileformat; docs/magpie-design.md, phase 2), no library's. Every write of a process goes through its sequencer (put, batch, commit): the rows are visible to the process at once and durable at the flush, and latest of one key (equal) reads its newest row from the image in memory. One file is at once the log entry (positions), the level-0 segment (sorted, with statistics) and the search index (word filters, and the counts a search's scoring reads). The numbering, the sequencer, the reads, the search and the catalog's state are the package's; a log is a directory path, a snapshot a position.

FunctionDescription
batch[dir, f, by = [], flush = true, time = '', narrow = [], stem = false]The frame written as the log's next batch through the sequencer — put and a flush: the rows take the next positions as they arrive, and the batch file (the directory made where it is not yet) is written sorted by the log's keys and flushed to the disk before the call answers (with flush false, left to the sequencer's thread, as put leaves it). The first batch fixes the keys as by — and the log's time column as time, the float columns — and the columns of vectors — kept in 32 bits on disk as narrow (lossy, a model's memory the only reason; the frame keeps 64 in memory), and whether the log's words are stemmed as stem (the Porter stemmer, for English, at the index and at the query), where given — in the manifest, and a later batch names the same keys or none; another set is refused naming both (the log at 'orders' is keyed by id, not by item), as is another time column or another narrow list. Nothing is indexed here: the merge indexes every text column, and a search reads a batch whole, so a producer declares nothing about what will be asked. Answers the first position its rows got. An error value of kind 'magpie' where the directory cannot be made, the frame has no rows, or a column named is missing
put[dir, f, by = [], time = '', narrow = [], stem = false]The rows appended to the log through the sequencer: the next positions as they arrive, visible to this process at once (the catalog's pending row, which every reader of the process reads as a file named <dir>/.pending@first-last), written as a batch file and flushed to the disk by the flush the put asks for (later: on a thread of its own compiled, where puts that arrive while it runs join its next run; at once under crow run -i), or by sync, batch, commit, merge or backup first — Redis's write path, the log its append-only file. Answers the first position. A crash before the flush loses the rows put since it: a write that must be durable before it answers is batch. rm of the log's directory, or of a directory above it, drops the rows pending with it, and the rows a flush was writing as it ran: the flush links its file only while its claim on the rows holds, and rm lets the claim go with the tail (the thread had written them into the directory afterwards, and into a log made again at the path). The first put of a log declares as the first batch does. Another process sees the rows once they are flushed; two processes writing one log have each a sequencer of its own, and a put's positions are the log's once flushed (a batch number another process took first makes the flush claim the next, as batch always did)
commit[dir, f, seen = -1, columns = [], equal = []]The sequencer's transaction: one that read at snapshot seen the keys columns[i] = equal[i] (each value as text) and writes f. Appended where none of those keys was written after seen; refused with an error value of kind 'magpie' naming the key and the position where one was (conflict: id = 2 was written at position 2, after snapshot 1). Reads that are the log's keys, in their order, are validated against the sequencer's index in memory — each key's last position, over the files once the image is built and every write since — in microseconds; any other read against every file and the pending rows. The write is put and a flush, durable before the call answers, its rows sorted by the log's keys as batch sorts them; two commits over one key serialise under the sequencer's lock. A commit that opens a log declares no keys
head[dir]The log's last position; -1 for an empty log
since[dir, from, upto = -1, columns = []]Every row at position from or later and at or before upto (every later row with -1), as one frame in position order: a consumer's read, its offset the last position it saw; a window, where the whole log is more than one read should hold — a read answers a frame, so a read over a billion rows is a loop over windows the program writes. columns names the ones to read, every column when empty (_pos read for the picking, dropped where not asked); a segment decodes only the columns asked, and a group whose positions all lie outside the window is not read; scan and latest take the same option
tail[dir, after, seconds]The rows past position after, waiting up to the seconds for some to arrive, polling every 20 ms; an empty frame when none came in time. A view that follows the log is a loop over tail: each call a batch of new rows, the view's state a frame it keeps, its results written back with batch for other views and other nodes to read
scan[dir, from = 0, upto = -1, columns = []]Every row of the log from position from up to position upto (every row with -1), in position order: each version of each key; a window of the log, as since reads one
latest[dir, upto = -1, columns = [], lo = '', hi = '', equal = []]The newest version of each key — the log's keys, as its first batch declared them — up to the snapshot, in position order: the table the log holds; every row where the log has no keys. With lo or hi, the keys whose first key column lies within them, each bound a value written as text as lookup takes one (latest['bars', lo = '2026-09-17', hi = '2026-09-17']; an empty one is no bound): a segment's groups are in key order, so the range reads the groups it covers — a window of the table, where the whole is more than one read should hold; refused for a log with no keys. columns names the ones to read, every column when empty — the log's keys and _pos are read beside them and answered with them, since the newest row of each key is found by them (a list lacking them had stopped the fold: sort: column '_pos' not found). With equal (one value per key column, each written as text as lookup takes one), the newest row of that one key as a frame of one row or none — a lookup in the image the sequencer keeps in memory (the table built from the log when first asked, kept current by every write after, the pending rows included), so latest['orders', equal = ['2']] takes microseconds; upto, columns, lo and hi are the files' and are refused with it, since the image is current and whole
search[dir, column, words, k = 10, snippet = 0]The k rows whose text column best match the words, with the files' columns and a score — and, with snippet more than 0, a snippet of that many characters each side of the first word found, at character boundaries, … where it is cut — the best first and an earlier position first between equals; the columns and score alone where no row matches. Each word is one of Lucene's forms: a word (read as its tokens, lowercased; a word of several tokens is a phrase), a phrase (a word with a space, 'kitchen table': the tokens in order, scored as one term whose count is the phrase's occurrences and whose idf is its tokens' sum, as Lucene's phrase scorer does), a prefix ('kit*': every term that begins so) or a fuzzy word ('kitchn~': every term within two edits, 'kitchn~1' within one; Levenshtein, as Lucene's fuzzy query takes it); a prefix or a fuzzy word scores each row it matches 1.0, as Lucene's multi-term queries do by default; a term asked twice counts once; the words are stemmed where the log declared stem. BM25 as Lucene's BM25Similarity scores it (k1 = 1.2, b = 0.75; an idf of ln[1 + (n - df + 0.5) / (df + 0.5)]; a word's weight tf / (tf + k1 * (1 - b + b * dl / avgdl)); a row's score their sum over the words it holds; lengths exact, where Lucene keeps a byte of them, so Elasticsearch's numbers differ past the second digit), over the whole log as one corpus. A segment is read through the index the merge built — per text column per row group a filter over the tokens, a sorted dictionary of them and each term's postings (the rows holding it, their counts and positions, in blocks of 128 each carrying its largest count and shortest document), and the group's document and word counts, which give n, df and the average length without the rows; a group whose filter admits no word is not read, and a block whose bound with the other words' cannot reach the k-th score is skipped — and a batch, or a group whose column the merge left unindexed (an identifier-like column, its distinct tokens past half its documents; a category-like one — a symbol, a day — fewer than one distinct token per 64 documents, whose filter over its values admits the group and whose rows lookup reads: the bars' two had cost 187 MB of postings on a 266 MB month, measured 2026-10-27), is read whole and counted as it is read. The ranking is the same either way: the index changes what is read, not what is scored (parity 296, 300). Held to the formula computed apart in tests/reference.py. An error value of kind 'magpie' for a column that holds no text, a negative k or a negative snippet
nearest[dir, column, vector, k = 10]The k rows whose vector column (see frame, a column of vectors) lies nearest the query vector — a tensor of one axis, or a list of numbers — by the cosine: the inner product of the row's unit vector and the query's, the score crow's vectors package's flat index computes, so the two agree row for row; with the files' columns and a score, the best first and an earlier position first between equals; the columns and score alone where the log has no rows. Exact over every row of the log, the pending rows included — a group at a time, file after file — a missing cell skipped; an index per segment (an HNSW of our own) is the step when a corpus asks for one, and a flat scan over a few thousand rows answers in microseconds. An error value of kind 'magpie' for a column that holds no vectors, a query of another width than the column's, or a negative k. Through the door: GET /orders/nearest?column=e&vector=1,0&k=5 (parity 303)
lookup[dir, on, equal, columns = []]The rows whose on columns hold the values equal, every pair at once, each value written as text ('3', '2.5', 'true'; a moment as its milliseconds), in position order: each file asked through its filters, and a segment through its row groups' statistics for every key, so keys the segment is sorted by read one group of a few megabytes (lookup[d, ['day', 'symbol'], [day, sym]] reads one symbol's day, not its month). columns names the ones to read, every column when empty; a segment decodes only those. An error value of kind 'magpie' for a column the log lacks, a value that is no value of its kind, or lists of different lengths
sync[dir]The pending rows flushed as a batch file, then every file of the log — its batches, its segments and its manifest — flushed to the disk, then its directory: what a put had left to the sequencer's thread; answers how many files were flushed
merge[dir, every = false]The log compacted in two moves. The tail's batch files are folded into a segment of level 1 (magpie.merger's merge_files: the streaming merge — one row group per input in memory, the rows in the log's keys' order then position, the latest version of each key kept, or every row with every for an append-only table whose keys are its sort order and no identity, refused where the log has no keys; a segment cut at a gigabyte and named by its counter, S000000000017.segment), the manifest switched to name it in one atomic replacement, the batches removed; then, while a level holds more than eight segments, its oldest eight fold into one of the next level the same way, so a billion rows are a few dozen segments over three levels and a merge touches one slice of the log. Across segments the newest position wins at read, as lookup and latest already read. A stale batch a crash left behind and a segment the manifest does not name are removed with the inputs. Answers the tail's segment's path, or '' where the tail held no batch to fold — a lone batch is folded too, so a merge answers the same however a flush cut the rows into files
metrics[dir]The log's figures as a frame of one row: files (the live ones: batches no segment holds, and segments), batches (not merged yet), segments, stale (batches a segment holds, not removed yet), rows (live), bytes (the live files on disk, sys filesize) and head (the last position, -1 for none). A table of its own: a program that keeps it writes it to a log of its own, as any table
backup[dir, to]The log's live files and its manifest copied under to — a directory (made where it is not yet) or an s3:// prefix (put) — and a listing written last naming them one per line, so a backup is whole only when its listing is: a version of the log. Answers how many files were copied. An error value of kind 'magpie' for a URL (http://, https://), which is read, not written, or a file that cannot be copied
restore[saved, dir]The files a backup's listing names copied into dir (made where it is not yet; an empty directory, or one whose files the backup's replace), each written whole, the manifest last; answers how many. A log is read by position, so a restore followed by the batches written since is the log as it was. An error value of kind 'magpie' where saved holds no listing, or is a URL
share[dir, port, host = '127.0.0.1', rounds = 0]The log served to its followers — replication by log shipping. A follower connects, asks for the live files' names and the manifest's (list: a count, then a name and its bytes per line) and for each file it lacks (get <name>: the size on a line, the bytes after it); a file is written once and never changed, so a follower that holds a file holds it whole, and the manifest is asked for every time. One loop serves every connection, each polled in turn, as the Kafka door does, until rounds loops have run (forever with 0). Answers how many requests it answered; an error value of kind 'magpie' where the port cannot be bound. A name with a /, or that is no batch's, segment's or the manifest's, is refused
follow[dir, host, port, seconds = 5.0]The files the shared log holds that dir lacks, fetched into it (made where it is not yet), each written whole, and the leader's manifest after them, every time; the batches a fetched segment covers let go, as the leader's merge let them go, and a segment the manifest does not name with them. One pass: a follower that keeps up calls it again, and between calls reads the log by position, as any log is read. Answers how many files came. An error value of kind 'magpie' where the server cannot be reached within the seconds, or answers other than a log's server does
summary[dir, by, of, how, on = [], ops = [], equal = [], lo = '', hi = '', upto = -1]An aggregate pushed below the reader (magpie.executor): over the segments and the tail, each row group pruned by its statistics, only the columns named decoded, the rows the predicates admit (on[i] ops[i] equal[i]: eq, ne, lt, le, gt, ge, each value written as text as lookup takes one; one column named twice is any of its values, columns are all of them) and the first key's range lo..hi and the positions at or before upto kept, grouped by the by columns (none for one row) and reduced, of[i] by how[i] — count, sum, min, max, mean, var (the population's), std, first and last by position — into a column of_how, the partials combined (sum and count for the mean, Welford's merge for the variance). A row per key in the keys' order, the key columns as they were; count an int, sum an int of ints and a float of floats, the means and deviations floats (a missing cell where a key has no present cell), min, max, first and last of the column's kind. It answers what group answers over scan of the same rows (parity 301), within the last digits a sum in another order moves, and the rows are never held as one frame: ClickHouse's behaviour on the queries most analytics are, the cost the bytes of the columns touched. An error value of kind 'magpie' for an aggregate or an operator that is none, lists of different lengths, or a text column summed
prior[dir, f, columns = [], upto = -1]The as-of join over the log (magpie.executor): for each row of f, which holds the log's keys and a moment in the log's time column (declared at the first batch, time = 'ts'; a moment, or an int of milliseconds), the newest row of the log with the same keys at or before that moment — by time, then by position — with its columns (every column of the log the labels lack, when none is named) beside the label's, missing cells where none precedes; the labels' columns first, in their order. upto is the position the join is as of (-1 is now): a row past it is no candidate, so a training set a position names comes out the same at every run. The frame module's join[…, 'asof'] with the log as the right side, read from each key's run in the key-sorted segments and the tail, the log never held as one frame: a training set of labels against a billion-row history. An error value of kind 'magpie' for a log with no keys or no time column, or labels lacking either
door[root, port, host = '127.0.0.1', rounds = 0]The HTTP door over every log under root (door, since a use web app's serve[port] is the server, and a program holds a magpie beside its app): a request's path names the log and the verb (/orders/latest; a log made by its first batch, as any path under the root; . and .. refused), the query its arguments (a list as comma-separated values, so a value holding a comma is not sent this way), the body its rows. By GET: head, since, scan, latest, lookup, search, summary, batches, metrics; by POST with the rows as JSON records: put, batch, commit, prior; by POST with no body: merge, sync. The answer a frame as JSON records, a number as itself, a refusal as {"error": …} with status 400, an unknown path or verb 404. One loop serves every connection, each polled in turn, as the Kafka door does, until rounds loops have run (forever with 0); answers how many requests it served; an error value of kind 'magpie' where the port cannot be bound. A log is a directory path or a URL: every verb given 'http://host:port/<log>' reaches the door with the same arguments and answers the same frame (latest['http://host:9000/orders'], batch['http://host:9000/orders', f]), so a program in another process, and any HTTP client, reaches one store (tests/doors.py, both modes)
batches[dir]The catalog's state: a frame of the log's files, a row each — number and high (the batch numbers it covers; -1 for the pending rows), form (batch, segment, stale for a batch a segment already holds, or pending for the rows put and not yet flushed, at the path <dir>/.pending@first-last; the pending rows are read before the files are listed, and left out where a file covers them, so a flush between the two steps shows the rows once), level (0 for a batch; a segment's level, one past its inputs'), path, rows, first and last (positions) — the segments as the manifest names them, the batches as the directory lists them, the pending rows as the sequencer holds them; one row with an empty path and last -1 for an empty log. A read prunes by it: since and scan by last, lookup and search through each file's own index. A reader that finds a listed file gone — a merge replaced it between the listing and the open — reads the listing once more and goes again

log[magpie.merge['orders']]            --- orders/S000000000001.segment
log[magpie.latest['orders'].qty]            --- [10, 25, 30]

Nodes and shards. A second node is a follower of the log (share, follow): it holds the same files and the leader's manifest, reads them with the same verbs, and serves what the leader serves; the leader is the one process that writes, and a follower promoted by the operator writes from the head it holds — there is no election, since every file a follower lacks is one follow fetches, and a leader that writes nothing more is followed to its last file. A table too large for one node is split into logs by a key (orders_a, orders_b, a directory each, on a node each), and a query runs the same verbs on each and stacks the answers: frame.stack[latest['orders_a', k], latest['orders_b', k]], or a reduction over each log's part. Nothing in the package knows a shard: the placement is the program's, written where the logs are named.

The parts

Each file of the package is a part a program may import as use magpie.<part> — the log above is built of them, and a program needing one alone (a file's bytes, a bloom filter, the stemmer) reaches it so.

lz77: use magpie.lz77

Magpie's codec, in Crow (docs/magpie-in-crow.md, the plan that rewrites every kernel of Magpie's in the language): the LZ77 byte codec a chunk's payload goes through where it shrinks it, the Rust kernel's stream byte for byte. A part of the package, as every kernel ported is.

FunctionDescription
compress[bytes]The bytes compressed: tokens of a literal run and a match (an offset of at most 65,535 back and a length of four or more), the last token literals alone; a short input is literals alone, a run shrinks to a few bytes per 255
decompress[bytes, raw_len]The bytes decompressed to exactly raw_len bytes; a stream that decodes to another count, is cut short, or reaches outside itself is an error value of kind 'magpie' saying why

bitpack: use magpie.bitpack

Bits and varints, in Crow: the two ways a number is written into a Magpie file, the Rust kernel's bytes byte for byte. A value is a 64-bit pattern held as an int, one at or past 2^63 the negative int of the same bits.

FunctionDescription
width_of[top]How many bits the value needs: 0 for 0, 64 for a pattern at or past 2^63
packed[values, width]The values at width bits each, little-endian within and across bytes; width 0 writes nothing
unpacked[bytes, at, n, width]n values of width bits each read from the bytes at at; an error value of kind 'magpie' where the bytes are too few or the width passes 64
put_var[bytes, v]A varint (LEB128) of the pattern's 64 bits appended
read_var[bytes, at]The varint at at and the position after it, as a list of two ints; an error value of kind 'magpie' where the bytes run out or the count passes 64 bits

columnchunk: use magpie.columnchunk

A column chunk, in Crow: the cells of one column over one row group as a Magpie file writes them, encoded by the column's kind and passed through the codec where that shrinks them, the kernel's bytes byte for byte. A chunk is an encoding byte, a flags byte (a presence bitmap follows; the payload went through the codec), the row count, the raw and the stored payload's lengths, the bitmap where cells are missing, then the payload: ints by frame of reference or by delta, whichever is smaller; floats as their bits, 32 of them where the column is narrow; text as bit-packed lengths and bytes, or as a dictionary and codes where the distinct values are at most half the cells; bools as a bitmap; moments as milliseconds and offsets; vectors as the rows' floats laid flat. The column's cells come and go as the vectors they are held in, never one at a time.

FunctionDescription
chunk[column, from, to, narrow]The chunk of rows from to to (excluded) of the column, as the file's bytes; a float or a vector column with narrow is written in 32 bits (encode and decode are the core's)
unchunk[chunk, kind]The column a chunk's bytes hold, its missing cells marked, kind the column's as the file's footer says (int, float, text, bool, moment, vector); an error value of kind 'magpie' where the bytes are cut short, promise rows they do not hold, or are no encoding of the kind
header[]The chunk's header alone, 14 bytes: what a reader reads before it knows how much the chunk holds

bloom: use magpie.bloom

A bloom filter over byte strings, in Crow: k hashes into m bits, the two hashes FNV-1a and a mix of it (double hashing: the i-th position is h1 + i·h2 modulo m), so a filter written today reads the same tomorrow; eight bits per item and six hashes, about 2% false positives; the kernel's bits bit for bit. What a file keeps per column chunk over its distinct values, and per indexed text column over its tokens.

FunctionDescription
sized[items]An empty filter for about items values (at least eight items' worth)
add[filter, bytes]The filter with the byte string's bits set
filled[filter, items]The filter with every byte string of the list added, in one pass over the bits (a group's distinct values, its distinct words)
admits[filter, bytes]Whether the filter may hold the byte string: never false for one it holds, true now and then for one it does not (has[…] is written key in m, so the word is admits)
filter_bytes[filter]The filter as a file holds it: its hash count, its bit count as eight bytes little-endian, its bits
filter_of[bytes]A filter read back from a file's bytes; an error value of kind 'magpie' where the bytes are too few or the counts cannot be

stemmer: use magpie.stemmer

The Porter stemmer (Porter, 1980), in Crow, for English: a log that declares stem applies it to every token at the index and at the query, so running, runs and runner all run. The algorithm's five steps as the paper gives them, over a word's bytes as ASCII letters; the kernel's answer word for word.

FunctionDescription
stem[word]The word's stem; a word that is not all lowercase ASCII letters, or has two or fewer, is itself

postings: use magpie.postings

A text column's index over one row group, in Crow: the lengths of its documents, a sorted dictionary of its terms, and for each term its postings — the rows holding it with the count and the positions, in blocks of up to 128 with the block's largest count and shortest document as the bound of the best score it can reach — so a query costs the postings of its words and not the column; the kernel's bytes byte for byte. The same counts a scan of the column yields, so a group with an index and one without score alike.

FunctionDescription
built[column, from, to, stems]The index of rows from to to (excluded) of a text column, each cell a document (a missing cell none), the tokens stemmed where stems: a record of its blob, its document count docs and its word count words
parsed[bytes]An index read back: the lengths, the terms in order with their dfs, where each term's postings lie (offs, lens) and the blob; an error value of kind 'magpie' where the bytes are cut short
term_of[ix, word], with_prefix[ix, prefix], within[ix, word, edits]A word's place in the dictionary (-1 for none); the places of the terms with a prefix, in order; the places of the terms within an edit distance of a word (at most 2), the nearest first
blocks_of[ix, term]A term's postings, block by block, each block its max_tf, its min_len and its posts (row, count, positions)
levenshtein[a, b, most]The edit distance of two words, cut at most (an answer past it is most + 1)

fileformat: use magpie.fileformat

A Magpie file, in Crow — one format for a batch, a segment and the manifest, the kernel's bytes byte for byte: the magic, then the row groups, each column's chunk (magpie.columnchunk) followed by its filters over the group (a value filter where the distinct values are at most 65536 — none for the position column, whose bounds prune by range; a token filter and the postings for a text column the log indexes, unless its distinct tokens exceed half its documents or fall under one per 64 of them); then a block per column with one entry per group; then the footer and its length and the magic again. A reader reads the last bytes, then the footer, then only what it is asked for — one column's block to prune by, one group's chunk to decode — and decodes the groups across the cores (every chunk read first, then a pure loop). Records: Bound (form 0 none, 1 an int or a moment's milliseconds in whole, 2 a float in real, 3 a bool in whole, 4 text in word), Entry (chunk_off, chunk_len, rows, absent, distinct — -1 where the column keeps no filter — lo, hi, bloom_off, bloom_len, indexed, tok_off, tok_len, docs, words, index_off, index_len), Meta (name, cells, indexed, block_off, block_len), Footer (rows, first, last, key_names, note_names, note_texts, groups, columns), Columns (names, kinds, indexed), Group (data, entries, rows), Reader (path, footer), About.

FunctionDescription

merger: use magpie.merger

The streaming merge, in Crow — batches and segments, each sorted by the log's keys then position, folded into segments of bounded size, the kernel's segments and manifest byte for byte. What is held is one row group per input and the rows not yet decided, in the merged order: a frame sort of what is held, stable and adaptive to the sorted runs it is handed. Each round decides every row at or before the least, in that order, of the last rows the inputs with groups left have loaded — no row an input has not loaded can come before it — and loads the next group of the input that row came from. Where the log keeps one version per key, the run of the bound's key is held back until a row of another key follows it, and a run decided keeps its last row, the newest. A group of the output is cut where its rows' bytes reach the group's size as the kernel counts them (8 an int or a float, 10 a moment, 1 a bool, a text's bytes and 4, 8 per number of a vector), a segment where its file reaches the segment's size. Records: Written (name, first, last, rows, bytes), Merged (written, counter).

Design Note: one file per commit, and the module over it. Considered: a write-ahead log of row-shaped entries, a memtable flushed to sorted segments and postings built beside them — three writes per row, three structures (rejected: every durable database pays them, and no reader of this log needs them apart: a batch file sorted by key with statistics in its head is the segment a scan prunes, the index a search prefilters, and the entry a consumer reads by position, so the row is written once at commit and again only when files are merged). Considered, for the kernel's reach: the sequencer in the runtime under a lock (rejected: the validation is policy, which is Crow's; the kernel claims a number atomically — a file linked into place only where none exists — and the Crow code validates every file before the number it claims, so a slip is a retry, not a hole). Considered, for the name: log (taken by the console), store (sys's store row), journal (rejected: long), lake (the first name, rejected 2026-10-26: the industry's word for raw files other engines query, where this store holds its state and runs its own engines), keep (a web option), hold (the spec's verb on every page), ledger (the log alone, not the engines over it), corvid (heard as covid) — magpie, the corvid that gathers everything into one nest, a bird as crow and finch are. The position column is _pos, a name no table of a program is likely to use; a frame that holds one is refused. A value looked up is written as text so that one function serves every column kind, compared with str of the column on both sides and read by the kernel as the column's kind for its filter.

Design Note: a manifest, and keys declared once. Considered: the directory as the catalog, as the first architecture had — every read listed the log and read every file's head to decide what to open (rejected 2026-10-26: the listing was the index, a merge's switch was two steps a crash could split, and nothing said which files were live); keys given at every call — batch[d, f, by = …], merge[d, by = …], latest[d, by] (rejected: a log sorted by one key at write and merged by another is a mess nobody wants, and latest by a column that is no key is a group over scan, in Crow); a second declared sort order, so a reverse-edges log for a graph would be the merge's work (rejected for now: a second order is a second log the program writes, two batch calls, and a package over Magpie does that; a declared order would double every merge for every log). Decided: dir/manifest, a Magpie file of one group naming the live segments (each its level, position range, rows, bytes and key ranges) with the log's keys in its key list and its declarations — the time column — in its notes, written beside and renamed over the old one; the batches stay the tail the directory lists. The first batch declares the keys; merge, latest and commit read them from the manifest and take no by; a batch naming other keys is refused naming both. What the manifest does not name is a leftover the next merge removes.

Design Note: the executor as operators. Considered: a query engine linked, as DataFusion (rejected 2026-10-26, Vijay's rule: nothing third-party in Magpie); a planner and a vectorised executor of our own, with a query vocabulary in Crow to drive it (rejected as a phase: a multi-year engine, and the boundary stated under what Magpie does not do). Decided: one kernel for the shape most analytics takes — filter, group, aggregate, sort — as separate operators over row groups (scan pruned by statistics, filter by predicates over column vectors, group by the keys' bytes, reduce into partials, combine), so a verb is a fixed composition and a later door a translator; predicates as three lists (on, ops, equal) because a mask is an expression no row can take and values written as text are what lookup already takes; the population variance, as the frame module's group answers it; first and last by position, so the answer depends on no order in which the groups are read. The as-of join beside it, over each key's run, for the point-in-time join a feature store is built on. Not here: joins of two large logs in one plan, subqueries, window functions — loops over windows in Crow.

Design Note: search's long tail, in our own code. Considered: Lucene's engine linked, as tantivy (rejected 2026-10-26, Vijay's rule: nothing third-party in Magpie). Decided: the pieces Lucene's long tail is made of, each written here and held to the scan — postings with positions per text column per row group, built by the merge beside the token filter (the filter stays: it answers whether a word can be in a group in microseconds, where a dictionary is parsed per group); a sorted dictionary, so a prefix is a run of it and a fuzzy word a walk of it with the edit distance cut at two; a block bound (the block's largest count and shortest document) so a top-k over a common word skips the blocks that cannot beat the k-th, at the granularity of a block of 128 postings and of a group; the Porter stemmer, declared per log so the index and the query agree; a snippet around the first hit; facets a group over the answer, in Crow. Not here: analysers beyond letters and digits lowercased, stemmers beyond English, Lucene's query DSL. The forms' syntax is Lucene's own inside the words (kit*, kitchn~, a space for a phrase), since a word is a text the program hands over and no syntax of the language's is touched.

Design Note: the sequencer. Considered: every write a file of its own, as the first architecture had — a row per request a file per request, thousands a second without a flush and hundreds with (rejected 2026-10-26: Redis takes single-key writes at memory speed, and Postgres groups its commits); a server process of the log's own, as Redis and Postgres are, every write a request to it (rejected for now: a log is a directory a program opens, and a served app is that process; the doors of phase 9 make it reachable from outside). Decided: one structure per log in the process — the memtable and its write-ahead log, which every durable database has — holding the rows written since the last flush with the positions they were given as they arrived, each key's last position, and the image of the newest row per key; every write of the process goes through it under its lock, a flush asked for through later writes what is pending as one batch file and fsyncs it, the puts that arrive while it runs joining its next run (a hundred a second is nothing), and the readers of the process see the pending rows at once because they are served as a file named <dir>/.pending@first-last, a Magpie file in memory the readers open as any other — one reader for the files and the memtable, as design rule 1 asks. The name carries the positions the listing saw, so a reader that opens it after the thread flushed those rows is handed the file they went to, and a listing reads the pending rows before it lists the files, leaving them out where a file covers them: a flush between the two steps hides nothing and doubles nothing (the first version listed the files first, and a head asked just after a put had answered -1). Positions a put assigns are provisional until flushed where another process writes the same log; one writer process is the design, and the kernel's claim of a batch number is the safety net it always was.

Design Note: reads bounded by what a frame holds. Considered: a read that answers a stream, so a billion rows could be walked by one call (rejected 2026-10-26: the language has one shape for rows, a frame, and a stream of frames is the loop the program writes). Decided: every read is bounded — since and scan by a position window, latest by a range of the log's first key, lookup and search by their keys and k — and a read over the whole log is a loop over windows in Crow, each window reading its segments and its columns and nothing else; an aggregate over the whole log stays such a loop until the executor of phase 8 pushes the common ones below the reader.

Design Note: indexes built by the merge, never by the producer. Considered: the producer naming the columns to index (texts on batch, as the first architecture had; rejected 2026-10-26, Vijay's question: an ingestion job should not know what will be asked of its rows, and a column it did not name was unsearchable until the log was rewritten); every batch indexing every text column (rejected: the price on the write path for columns never searched, and the decision still at ingestion). Decided: the merge indexes every text column of every segment it writes, per row group, giving a column up where its distinct tokens exceed half its documents (an identifier column: a filter of every value prunes nothing); a search reads an indexed group through its filter and any other group whole, and scores both the same, so a row is searchable the moment it lands, cheap once merged, and no producer decides either. A batch's own words are not indexed: the tail is small because the merge runs.

Design Note: the streaming merge and its levels. Considered: every merge folding every file into one segment, as the first architecture had (rejected 2026-10-26: the merge stacked every live file into one frame, sorted it and wrote the segment into one buffer — it ended at RAM — and every merge rewrote the whole log); segments in position order with blooms alone for the keys (rejected: it gives up the one-group lookup by the keys a segment is sorted by, the thing the measure showed); key-ordered levels with disjoint ranges, as LevelDB keeps them (rejected: a log compacts by time, and disjoint key ranges make since read every segment). Decided: a k-way merge over inputs that are already sorted by the keys then position, one row group per input and one for the output in memory, the newest version of a key the last of its run; segments of at most a gigabyte, named by a counter since a merge that splits by size makes two over one position range; levels with a fan-out of eight, the tail folding into level 1 and a level's oldest eight into the next, so a merge touches a slice and a billion rows are a few dozen segments; across segments the newest position wins at read, which lookup and latest already do.

Design Note: Magpie's own file format. Considered: Arrow IPC for a batch and Parquet for a segment, as the first architecture had, the statistics as one JSON text in the file's head (rejected 2026-10-26: no third-party code in Magpie — Vijay's rule; and three costs of their own: the head was parsed whole by every query of any column, tens of megabytes at a thousand columns; Parquet keeps a footer entry per column per row group, so a billion rows in groups of 8192 was the known wide-table pathology; every write converted the frame to Arrow and every read converted it back). Decided: one format for a batch, a segment and the manifest, designed around the frame's columns — a chunk is a column's cells over a row group as the frame holds them, encoded by its kind; the index is per column, found through a two-level footer, so a reader reads the one column's one group; the codec is our own, applied where it pays. Format 2; format 1 is not read, since nothing was released.

The Kafka door: use magpie.kafka

Import with use magpie.kafka; the door is kafka.serve[…]. The Kafka door of the magpie, written in Crow on the sys layer and use magpie: a topic is a log under the door's root (<root>/<topic>, one partition, its positions the offsets), a producer's records are appended as one batch (at, key, value, and the producer's own offset as it wrote it; the log's position is the offset a consumer sees), a consumer's fetch is since from its offset, and a group's memberships and committed offsets are two logs of the door's own (<root>/_groups, <root>/_offsets). The protocol is the one a 0.10.1 broker speaks — ApiVersions says so, and every client then writes and reads legacy message sets of magic 1 — framed, parsed and answered in Crow; the per-byte half, a message set to a frame and back with its checksums, is magpie.recordsets' (message_rows, message_set). The door serves every connection from one loop, each polled in turn for its next request, so both modes run it the same way.

Considered: the current protocol (record batches of magic 2 — varints, CRC-32C, headers, compression — and flexible request versions with tagged fields) (rejected for the first door: a client reads the broker's ApiVersions and speaks what it says, so a door that says 0.10.1 is spoken to in legacy message sets, a fixed layout with one checksum, by every client written since — the pure-Python client, librdkafka's, the Java one — and the record kernel is a page where the current format is a chapter; the current format is the door's next step, behind the same records rows). Considered: a thread per connection (rejected: the interpreter runs later inline, so a door that spawned would serve one client at a time interpreted and many compiled — the two modes must run the same way — and a Kafka client opens several connections at once: one for metadata, one per broker, one for its group's coordinator; one loop polling each connection, waiting five milliseconds at a time, serves them all the same way in both modes). A topic's one partition is the magpie's one log; partitions would be logs under the topic, and are not made until a client asks for them.

The RESP door: use magpie.redis

Import with use magpie.redis; the door is redis.serve[…]. The RESP door of Magpie, written in Crow on the sys layer and use magpie: a Redis client connects to the port and speaks RESP2 as redis-cli and every client library write it — a request an array of bulk strings, a reply a simple string, a bulk string, an int, an array or an error — and the door answers from Magpie. The keys and values live in one log under the door's root, <root>/_kv, keyed by key, a row per write with a dead flag for a deleted key: a GET a read of the sequencer's image in memory, a SET a put, flushed by the sequencer's thread. A stream is a log of its own, <root>/<name>: XADD a put, the entry's id its position (12-0), XRANGE and XREAD reads by position.

FunctionDescription
serve[root, port = 6379, host = '127.0.0.1', rounds = 0]The door: listens on the host's port and serves every connection from one loop until rounds loops have run (forever with 0), answering how many requests it served; an error value of kind 'redis' where the port cannot be bound. Answered: PING, ECHO, SET, GET, EXISTS, DEL, INCR, INCRBY, MGET, MSET, KEYS (* or one key), DBSIZE, XADD (* ids only), XLEN, XRANGE (-, +, an id), XREAD (STREAMS, one stream, the entries past the id; no BLOCK); any other command, or a wrong count of arguments, an error reply naming it. Held to a client of the test's own in both modes (tests/doors.py)

Design Note: a door per protocol, not a protocol of our own. Considered: Magpie's own wire protocol with a client library per language (rejected: every language already has a Redis client, a Kafka client and an HTTP client). Decided: the Kafka door's pattern applied again — a protocol written in Crow over the sys listener, each command a verb of the log — so the clients of three products reach one store; expiry (EXPIRE, TTL) waits on the expiry column, and the commands over Redis's structures (lists, sets, sorted sets) are not here: a sorted set is latest sorted, a list is the log.
