Magpie in Crow: the kernels rewritten, and what the language gains for it

(Moved here from the crow repository's docs/ on 2026-10-30, when Magpie became a repository of its own: a path below that names crow's sources — src/, crow_runtime/, tests/parity/, the Rust tests — is the crow repository's, as it was when written; Magpie's own files are this repository's packages/, examples/ and tests/.)

(Since 2026-10-29 Magpie is a package, packages/magpie: the modules this note ports are its parts, under its files' names — codec is lz77, packing bitpack, encode columnchunk, file fileformat, tail sequencer, merge merger, exec executor, search searcher, nearest knn, stem stemmer, records recordsets — and their tests run from there: crow test packages/magpie/lz77.co.)

Decided by Vijay, 2026-10-27: a package is written in Crow, and its author writes no Rust. Magpie is the first package held to that rule, and it is the hardest case, because two thirds of it is Rust today: the kernels under crow_runtime/src/magpie/ (7,500 lines: the file format, the codec, the encodings, the merge, the sequencer, the executor, the postings and the search, the nearest scan, the bloom filters, the gzip and snappy decoders, the stemmer) and the Kafka records kernel (crow_runtime/src/kafka.rs), reached from the Crow modules through nineteen rows of the sys layer. This document is the plan to rewrite every one of them in Crow, held to the Rust original as the oracle, and the five things the language lacks for that, each checked against the spec for an existing way (design rules 1 and 24).

What stays Rust is the language's own: frames, tensors, text, sockets, the core pool, the compiler. crow_runtime keeps its kernels; a package gets none.

1. The rule, and what it costs

A kernel written in Crow runs at the interpreter's speed under crow run -i and at the compiled program's under crow run. For per-byte work the interpreter is two orders slower than Rust, so a package's kernels must be compiled ahead of the programs that use them: the assembly step of the package plan (docs/magpie-repo-design, to be written) compiles the functions a crowfile names and registers them as rows the interpreter calls natively, so both modes run the same compiled code. Until assembly exists, Magpie's kernels inside the standard module run interpreted under crow run -i: correct, held by the same tests, and slow. The measures in docs/magpie-design.md are re-run in compiled mode at the end of the port and the interpreted numbers stated as they are, which is the case for assembly.

Compiled Crow over bytes and ints is the evidence the port stands on: revcomp, k-nucleotide and fasta run within a small factor of Rust, after the emitter's work on text builders, plain vectors and known-ASCII reads. The CSV parser that measured 20 to 45 times slower than the runtime's did per-cell work through values that can fail; the primitives below are chosen so a kernel never does that.

The first kernel ported is the codec, and it is measured against its Rust original on the same input before the second is begun: if compiled Crow lands within about two times, the port goes on; if not, the emitter is where the work is, not the kernels.

2. What Crow lacks, and the form each takes

Every item below was searched for in the spec first. Where a form exists it is extended by kind or by an option, never doubled.

2.1 Bytes written in place

What exists: bytes[text], text[b], len[b], byte[b, i], slice[b, from, to], find[b, needle], concat[a, b], pack, unpack, ieee[x], hex, hash, digest, hmac, random[n], mask, xor, same. A bytes value is Bytes(Vec<u8>) in the runtime, held plain in both backends. What a kernel lacks is writing: a decoder builds its output a byte at a time, an encoder writes lengths into what it wrote, a hash table of positions is a vector of ints.

  • bytes[n]: n zero bytes (a second bytes row, by kind, beside bytes[text]).
  • set[b, i, v]: the byte at i replaced by v, 0 to 255, counted from the end when negative, outside stops (the set the lists and maps have, for bytes).
  • push[b, v]: the byte appended (the push the lists have).
  • concat[a, b] with a moved: appended where a lies.

All three in place through what exists: Prop::InPlace on the row, a take bridge for the interpreter's moved argument, a taken path the emitter prints when the first argument is a moved local (taken_in_place splits b = set[b, i, byte[b, j]] as it splits a list's). Reads stay byte[b, i]: a kernel's loop reads and writes by position, and the vector of ints a hash table needs is a one-axis tensor, which the emitter already keeps as Vec<i64>.

2.2 Numbers in bytes

What exists: pack[n, width] and unpack[b, at, width] are big-endian and signed, as Kafka's wire is; ieee[x] is a float's eight bytes, big-endian. Magpie's format is little-endian with unsigned lengths, and a decoder reads floats.

  • pack[n, width, little = false], unpack[b, at, width, little = false, signed = true]: the options, defaults as today.
  • ieee[x, width = 8, little = false], and ieee[b, at, width, little]: the bytes at at as the float they spell (a second ieee row, by kind, the inverse of the first), 4 for single precision; the reader's width and byte order are positions, since an option may be given by position and ieee[b, at, 8] would be the writer's row with a width and a byte order.
  • digest[b, 'crc32'] and hash[b, 'crc32']: the checksum gzip and Kafka's message sets carry, four bytes, written by us as the other digests are not (a table-driven CRC-32 is twenty lines; the spec's "what stays native" note names no crate for it).
  • wrapmul[a, b], wrapadd[a, b], wrapsub[a, b] in use bits: the product, sum or difference of two 64-bit patterns wrapped to 64 bits, the int of the low bits. A hash (FNV's multiply per byte, murmur's mix), a linear congruence and a checksum are written on wrapping arithmetic, which a language whose ints grow has no way to say: the product of two ints past 2^32 is a growing int, exact and slow, and bitand of it with a 64-bit mask is a growing int's operation too. The three rows answer a 64-bit int, so the width pass keeps what is computed from them narrow.

What the width pass needs from a kernel's loop, found porting the codec and the packing: bits gather by bitor, never by +, since a sum in a loop is a growing int to the pass and bitor of two non-negative ints is bounded by the larger's power of two; a value wider than 32 bits is packed as its low 32 bits and its high bits apart, so no shift passes 64 bits; and a 64-bit pattern at or past 2^63 is held as the negative int of the same bits, assembled as lo + shift[hi, 32] where hi is read as signed in a branch the pass bounds. CROW_WIDTH_DEBUG=1 shows the settled ranges; a kernel is not done while one of its loop's ints is wide.

2.3 Files

What exists: file[path] (bytes, whole), store[path, bytes], filesize[path], read, write, exists, mkdir, ls, rm. The write path of a batch is: write a part file, flush it to the disk, link it into place (never over an existing name), flush the directory. A reader opens a file's footer, then one chunk. The footer cache is keyed by path, size and modification time.

  • file[path, from, n]: the bytes of a region (a third file row, by arity).
  • modified[path]: when the file was last written, a moment.
  • flushed[path]: the file, or the directory, written through to the disk (F_FULLFSYNC on macOS, fsync elsewhere); answers the path.
  • link[from, to]: a hard link, refused with the system's reason where to exists; answers to.
  • move[from, to]: renamed over to, atomically, as a manifest is replaced; answers to. (rename is the frame module's.)

2.4 Process memory

What exists: top-level variables, invisible to functions; facts, a served app's state, typed by their declaration and held by the session layer; env; the notes a connection keeps (note, noted: text, per stream). Nothing a module's functions can hold between calls for the process, shared by its threads. The sequencer is that: the rows put since the last flush, the key index, the image of each key's newest row; so is the footer cache, and the registry of what a process has opened.

  • remember[name, v]: the value held for the process under the name, replacing what was held.
  • recall[name, default]: the value held, or the default where none is; typed by the default, as env[name, default] is answered by its default's shape.
  • forget[name]: nothing held under the name.
  • revise[name, default, f, x]: f[held, x] run under the name's lock, with held the value held (the default where none), the value f answers held afterwards and answered; f owns the value it is handed, so a map's insert or a list's push inside it is in place. One schedule at a time per name, so two handlers writing one log serialise by construction, as the Rust sequencer's lock serialises them.

The store is per process and per mode: the compiled program keeps typed slots, the interpreter its values; the semantics are one. Two effect kinds carry the rules: held for a read, held.write for the rest, allowed and refused where db.read and db.write are (a view reads neither; a derivation reads, never writes), ordered in a loop for the writes, recorded by no rehearsal since nothing leaves the program. One kind of the row vocabulary is new: Kind::Any, the kind of the argument handed where it is taken, which types recall's answer by its default and revise's function by its default and the rest of its arguments, as later[f, a, b] hands its rest to f.

Design Note, recorded here for the spec: a timer was considered for the sequencer's flush and rejected again (the spec's "Periodicity Is Declared, Not Written"). A put appends to the process's memory and schedules later[flush_all], with no argument, which is allowed in a handler too: coalesced, so a burst of puts shares one flush; waited for at exit, so nothing put is lost to a clean end; run inline by the interpreter, so under crow run -i a put is durable when it answers, which is a legal schedule and a slower one. The ten milliseconds of the Rust thread become "as soon as the loop is free".

2.5 Columns as their parts

What exists: a loop over a column yields its cells, each a value that can fail where the cell can be missing; df.name reads a column and df.name = values writes one from a list, a tensor or a column; a frame's columns. What the writer and the reader of a file do instead is read a column's rows start..end as the vectors they are held in and build a column from such vectors, with no value per cell: the Rust writer encodes Vec<i64> and a validity bitmap; the reader hands the frame a Column it decoded whole. The CSV parser's factor came from the per-cell path, and the file format's chunk is the vector's shape.

Rows of the sys layer, each over a column and a range of its rows, answering what a chunk holds: ints_of[col, from, to] (missing as 0), floats_of, bools_of, millis_of and zones_of for a moment column, vectors_of (the rows' floats laid flat) with vector_width[col], text_bytes_of with text_ends_of (each cell's end offset, as the text is held), present_of (the validity as a bitmap's bytes, bit i of byte i / 8, the chunk's own layout, empty where every cell is present), and cell_kind[col] (int, float, text, bool, moment, vector). The inverse builds a column from its parts: ints_column[ints, present], floats_column, bools_column[bits, present], moments_column[millis, zones, present], vectors_column[width, floats, present], text_column[bytes, ends, present], each a Column the program writes onto a frame with df.name = …, which exists. A distinct count is exact: a map keyed by a 64-bit hash of the cell's bytes holding the byte strings that share it, compared with same.

2.6 Parallel decoding

Nothing new. A loop over file reads is ordered, since a read is an effect; a kernel reads the groups it needs first, then decodes them in a loop with no effect, which the compiler runs across the cores.

2.7 Packages and the sys layer

use sys had been refused in a program and allowed in a standard module. A package that holds kernels needs it: bytes, files, hashing, memory. Proposed: a package's parts may use sys. Decided wider (Vijay, 2026-10-29): keeping sys and memory to the standard library is a suggestion, not a rule — any program or package may import them, and a package that needs a kernel's speed is written on them.

3.1 Ported so far (2026-10-27)

magpie.codec, magpie.packing, magpie.encode (the chunk: every column kind, the kernel's bytes byte for byte, tested in both modes, the long columns through the codec), magpie.bloom (the filter, bit for bit, its positions held to the kernel's over ten thousand probes), magpie.stem (word for word) and magpie.postings (the index of a row group, byte for byte, blocks included). Two traps a kernel in Crow meets, recorded for the next ones: a list literal of ints ([h, g]) is a tensor, which holds a 64-bit pattern as a float and rounds it — two hashes travel in a record; and % keeps the sign of its left side, so a pattern read as unsigned is x % m, made non-negative, plus 2^64 modulo m, modulo m again. What the port added to the language beyond section 2: wrap[x] (a growing int's low 64 bits), float_bytes/float_values (a chunk's floats at once), and text_dict_column (a text column kept as its dictionary, as the chunk holds it). What it found: a module row's call printed without the owned-kind rule (a list moved at every call, E0382), encode and decode being the core's names (the exports are chunk and unchunk), and the interpreter's placeholder for a missing float cell (NaN) differing from the compiled program's (what was written) — the column rows read a missing cell as one placeholder now, in both modes.

magpie.file (2026-10-28): the file — the writer in parts (columns_of, group_bytes, finish, and file_of over them, so a merge can stream groups), the statistics and the token index with the kernel's rules, the reader by region (opened, entries, groups_of, the filters, about) — held to the kernel through file_rs byte for byte (plain, narrow and stemmed) and to batch_read/batch_stats on the way back, the torn and foreign files refused in the kernel's words, the same program run in both modes. What the measures found, each fixed with its test:

  • The sequencer flushed one put at a time. A flush wrote and synced its file inside revise, holding the tail's lock, and a put waits on that lock: each put waited out the last one's fsync, then asked a flush of its own row (2,000 files of one row; 61 s of system time). The kernel held the lock for its write too, but flushed from a timer every 10 ms, so puts gathered between flushes. Now the flush claims the pending parts under the lock, writes them outside it and lets them go under it (_claimed, _written, _settled): the puts that arrive during a write join the next flush, with no timer. The write goes to a file of the claim's own, linked into the batch's name under the lock only while the claim holds (_committed): rm forgets the tail before it removes the directory, so a log removed while its flush ran keeps none of its rows. A flush written wholly outside the lock had put them into the log made again at the path, and trimmed that log's own pending rows as it settled (parity 434). A listing that met a flush between its two reads begins the pending rows past the file that covers them (_uncovered), and pending_rows cuts at both ends, so no row is read twice or missed.
  • A revision that can fail copies the record first. A put's and an image's revisions answered errors, so every put and every latest copied the tail with its pending parts; they answer a refusal in the record now (refused), and latest is the kernel's again.
  • An item of an item was copied whole. by_cells[k][i] compiled to a copy of by_cells[k] for each read — the summary copied a group's cells once per row and column (quadratic in the group's size). The emitter reads the inner item where it lies (item_place).
  • A value a guard made known good was copied where it was lent. A reader handed to entries[r, c] carried its whole footer into a copy at every call, and a search's positions were copied per row it scored.
  • A search read a whole group for each of its k rows, reopening the file (its footer parsed again) each time, and opened the file again for every group it scored. The kernel kept its readers and a map of the groups it had read; the port does now.
  • A 64-bit hash ran on growing ints. The width pass read bitxor of a side spanning [-2^63, 2^63 - 1] as 65 bits, so the bloom filter's FNV and murmur over every cell a merge writes were big-int arithmetic; and a vector column's distinct count formatted 512 bytes of hex per row through format!.
  • nearest indexed rows through a growing int: row * w is past 64 bits to the width pass, so every number of every row was read through Int::add. It walks the flat list a width at a time now, within the list's length.

The second round (2026-10-28 to 2026-10-29), each fixed with its test:

  • The decoders ran on growing ints. A bit-packed column's decode read through a cursor and a count the width pass could not bound, and an unpack of 1, 2 or 4 bytes was any 64-bit int to it. Each width has a loop of its own now, written so the pass bounds the bits held, and an unpack reads within what its bytes spell (IntRange::Unpacked): a column's scan over finch's 11.3 million bars, 224 → 79 ms.
  • A graph's hop read the log once per node. A hop of more than four nodes reads its frontier as one range of the edges' log (packages/kg, _hop): a walk of 3 hops, 1,372 → 25 ms.
  • Bytes appended from a range were two copies. concat[a, slice[b, i, j]] made the slice, then appended it; the lowering fuses it (core.__concat_slice, and a = concat[a, slice[a, i, j]] into core.__extend_within), and the decompressor copies an overlapping match as whole repeats, doubling each time: 50 MB decompressed, 34 → 18 ms.
  • A scanned search placed every word of every text in the text's map of words. It places the words the query asks, unless a prefix or a fuzzy word asks of every word; it reads a field of a hit where it lies (a compiled program had copied a record that can fail out whole at each field read); and sys.tokens reads ASCII text a byte at a time: 105 → 53 ms.
  • The summary was a record per cell. A unit's rows are grouped once, by one int column through a map of ints, a column of numbers keeps its partials per group as numbers, and the groups' counts are added where they are held, so the width pass bounds them (through a local, every row's count had been a growing int): 109 → 6.9 ms, the answers the same to the digit.
  • A merge skipped a lone batch, so whether a key's older versions were folded depended on where a flush had cut the rows into files — which a compiled program's flush thread decides by its timing (parity 303 counted a summary differently in one run of three). It folds a lone batch too.
  • The writes looked a map up per cell, and the bloom filter's slots grew. A number column's distinct values are found by sorting them, and 2^64 modulo the filter's size is computed so the width pass bounds it: 200,000 × 102 written 5.3 → 2.83 s, merged 5.6 → 2.95 s, the files the same byte for byte.

What is left, and why:

  • Every read parses the file's footer again, and every entries call its block: the kernel kept both for the process (keyed by path, size and change time). Decided (Vijay, 2026-10-28): nothing is kept between calls — process memory is the standard library's and a program's never, and a form a derivation could call to keep a record was declined — so the reads are made cheap instead (the second round's first two items, and a read parsing only the groups and columns it asks). What keeping nothing still costs: the indexed search decompresses every index block it reads at every call, two fifths of its time in the decompressor's copies (2.4, where the kernel kept the blocks it had read), and nearest reads its column of vectors from the file at every call, 51 MB at 100,000 × 64 — two fifths of its time in read from the page cache and a quarter making numbers of the bytes (2.4, where the kernel kept them). A read of a region into numbers where they land, or a mapped file, would narrow both without keeping anything.
  • The summary, 3.5: each row's group is found through a map (a lookup to ask, another to read), each cell's presence is a call reading the bitmap, and the key column and the positions are decoded whole, where the kernel grouped in Rust over the column's bytes.
  • The scanned search, 4.8: each text is split into a list of words, a string allocated per word, and each word is matched against the asked words' map, where the kernel hashed the words where they lay. A row that counts the asked words of a text in the runtime would close most of it; it would be a native kernel, which design rule 20 asks a reason for.
  • finch's copies and merges, 1.8 to 3.6: a copy writes through batch by the table's keys, so each row's key is made into text and its position kept under a name of its own in process memory (<dir>/#last/<key>), behind the registry's lock and hash — 30 million names for the month's bars and quotes, where the kernel kept one hash map per log. The newest row of each key is already built when first asked; the index built the same way would take it off a bulk write. A merge's time is mostly the validity bitmaps made again from truths, the encoder and its compression.
  • Growing ints at the edges. 41 of the modules' functions still take or answer a growing int — a position, a count, a batch's number — a few operations per call; in the profiles of the measures above they are at most a percent or two of the time.

5. Open for Vijay
